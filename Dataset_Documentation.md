## Overview

SIFT-PROOF was evaluated against 7 benchmark forensic datasets and 1 extended stress evaluation. Cases 2, 3, 5, and 7 were provided directly by the SANS Find Evil! Hackathon 2026 organizers. Cases 4 and 6 are publicly available Ali Hadi DFIR challenge images. Case 1 is a synthetic scenario generated to validate anti-forensic detection. The Vanko case is an extended stress evaluation on a large segmented image provided by the hackathon organizers.

### A Note on the MFT Record Cap

Cases 1–7 were originally run with a 20,000-record MFT ceiling — a deliberate development control to keep runtimes predictable during initial validation. After the Vanko stress evaluation revealed this as a constraint worth removing, the cap was raised to 500,000 records and Case 4 was re-run at full filesystem scale (125,073 MFT records). Both runs are archived. The re-run result was identical: zero malicious findings.

## Case 1 — Synthetic Anti-Forensics Demo

**Source:** Generated by `data/create_test_data.py` — fully reproducible with `python3 data/create_test_data.py`.

**Why synthetic:** This case was designed to validate temporal contradiction detection. The capability requires specific data conditions — an MFT deletion timestamp that precedes a Prefetch execution timestamp — that cannot be guaranteed to appear in any given real-world image. The synthetic dataset was constructed to prove the system detects this pattern reliably.

**What the agent found:**

| Finding ID | Artifact | Detail | MITRE |

| `a77a018b` | `registry_runkeys` | `evil.exe` configured to run at startup via a Run registry key | T1547 |
| `6f8b4f23` | `mft_events` + `prefetch_events` | Temporal contradiction: deletion timestamp precedes execution timestamp — anti-forensic timestomping | T1070.006 |

**Gate events from audit log:**

**Validated capability:** Temporal contradiction detection and anti-forensic inconsistency reasoning across MFT and Prefetch artifacts.

## Case 4 — Ali Hadi Challenge #9: Encrypt Them All (E01)

**Source:** Ali Hadi DFIR Challenge #9 — publicly available at [ashemery.com/dfir.html](https://www.ashemery.com/dfir.html)

This case is the most important precision test in the dataset.

### Original Run (20,000-record cap)

**Audit log:** `logs/audit.jsonl.20260607_161105.bak`

All mandatory artifact categories queried. No claim survived the assertion gate. Zero malicious findings filed.

### Full-Scale Re-run (125,073 MFT records, 500,000-record cap)

**Archive:** `logs/cases/CASE-20260612-195810-Case4_ReRun_Extended.json`

After the MFT cap was raised, this case was re-investigated at full filesystem scale. Three findings were confirmed. None of them are malicious:

| Finding ID | Artifact | Detail | Assessment |
|-----------|---------|--------|-----------|
| `86b58812` | `mft_events` (125,073 rows) | Full filesystem timeline collected — coverage confirmation artifact | Benign — tool coverage |
| `d109c695` | `prefetch_events` (184 rows) | Execution signature set confirmed — coverage confirmation artifact | Benign — tool coverage |
| `8e1f788c` | `mft_events` | 7-Zip installer present in user Downloads directory | Benign — common installer |

The agent's final conclusion at 125,073 records: *"No evidence of malicious services, scheduled tasks, or web shells. Registry Run keys returned only legitimate entries. Event logs contained failed logon records only. The case is closed."*

**Result across both scales: identical — zero malicious findings.**

What changed between the original and the re-run is not the outcome. It is the confidence in that outcome. At 20,000 records, a ceiling argument exists. At 125,073 records, it does not. The precision gate held at both scales.

**Validated capability:** False positive resistance and precision under ambiguity — at constrained and full filesystem scale.

| Artifact | Rows | SHA256 |

**What the agent found:**

| Finding ID | Artifact | Detail | MITRE | Assertion SQL |

| `87697a98` | `memory_network` | `svchost.exe` maintaining 190 persistent outbound connections to non-RFC1918 addresses including `81.30.144.115` and `213.202.233.104` — consistent with C2 communication and exfiltration behavior | T1041 | `SELECT * FROM memory_network WHERE process_name = 'svchost.exe' AND remote_addr NOT LIKE '10.%' AND remote_addr NOT LIKE '192.168.%' AND remote_addr NOT LIKE '172.%'` |

This finding must be read alongside Case 7 for full forensic meaning.

**Validated capability:** Memory-resident threat detection via network connection analysis.

**Cross-case synthesis — Cases 5 and 7 together:**

- **Case 5 (Rocba Memory):** `svchost.exe` maintaining 190 active external connections to `81.30.144.115` and `213.202.233.104` — active in volatile memory.
- **Case 7 (Rocba Disk):** No dropped binaries, no persistence, no known tooling, no attacker artifacts on 224,343-record filesystem.

The synthesis is unambiguous: **fileless malware operating entirely in volatile memory, with no on-disk footprint.** The evasion model that peer-reviewed research identifies as increasingly dominant precisely because it defeats disk-based detection (Kara, 2022; IEEE, 2025). No single-image analysis tool arrives at this conclusion. It requires holding both findings simultaneously and reasoning about what their combination means.

**Validated capability:** Cross-artifact reasoning across memory and disk. Detection of the attack pattern visible only in the negative space between two individually clean-looking images.

## Extended Stress Evaluation — Vanko Student Case

**Source:** SANS Find Evil! Hackathon 2026 provided evidence — segmented E01 (×21 segments, E01 through E21).
**Download:** [SANS Hackathon 2026 Evidence Repository](https://sansorg.egnyte.com/fl/HhH7crTYT4JK#folder-link/HACKATHON-2026)

The Vanko case was not a standard benchmark run. It was a deliberate architectural stress test against the largest and most complex dataset provided by the hackathon organizers.

**Artifact counts from log:**

| Artifact | Rows | SHA256 |
|---------|------|--------|
| `mft_events` | 194,563 | `2c7e3a1e7ac9f50afcc99c574ff929aab7014b8462646556e06ee5e5c11601c7` |
| `amcache_entries` | 3,347 | `327034d66e93ff624088aba2cb03fdf4b7d8bb7a7263b4d270b4e8b30333260a` |
| `prefetch_events` | 153 | `2596d6be7789259b459a3ef896bd09e3ac6d9f74e3d3982971180472e14d2456` |
| `registry_runkeys` | 19 | `a7355f7a27c4e671a9540ca58e115217cf2adc1799c72e5d7b6d0c96a494a1f5` |
| `evtx_events` | 34 | `dfcd33509e1e2d65e16f238b45fa22a30411a34c4d4155ddf94b67c080da663c` |

**What the agent found:**

| Finding ID | Artifact | Detail |
|-----------|---------|--------|
| `a17465e1` | `mft_events` | Deleted executable `$RXTZCI7.exe` found in Recycle Bin — possible malicious payload removed to Recycle Bin rather than permanently deleted |

One finding confirmed. The Recycle Bin naming convention (`$R` prefix) indicates the attacker deleted the executable via normal Recycle Bin deletion rather than `Shift+Delete` — an imperfect cleanup that left a recoverable artifact.

**Four architectural constraints exposed:**

**1. Evidence dilution under high volume.** At 194,563 MFT records, high-signal artifacts — including the Recycle Bin payload — became statistically obscured by benign entries. Without targeted query expansion, the agent defaulted toward high-frequency artifacts rather than low-frequency anomalies.

**2. Query anchoring bias.** Early hypothesis formation caused premature path specialization, demonstrating the risk of overfitting an initial investigation model against a large evidence space before fully reading the environment.

**3. Conclusion compression.** During final summarization, distinct low-level artifact signals were aggregated into generic indicators, reducing forensic precision and collapsing traceable evidence chains.

**4. Coverage metric misalignment.** The system reported 100% tool coverage while high-value artifact paths remained underexplored — exposing the gap between structural completeness and investigative confidence.

**Engineering decisions derived from this case:**

- MFT record cap raised from 20,000 to 500,000
- Case 4 re-run at full filesystem scale to validate the cap removal
- Architectural roadmap defined for second-pass deep search, multi-artifact correlation graph, and investigative confidence scoring

This case is documented not despite its stress results — but because of them. Knowing where the system's reasoning depth ends is a more trustworthy starting point than not knowing.

**Audit log:** `logs/audit.jsonl.20260608_165114.bak`
