## Case 2 — NFury Windows 7 (E01)

**Source:** Ali Hadi DFIR competition image, widely used in DFIR training communities. The image is a Windows 7 Enterprise disk with a simulated intrusion scenario. Available at: https://github.com/ashemery/LinuxForensics

**Image hash (MD5):** Available in competition release documentation. Not reproduced here to respect competition distribution terms.

**What the agent found:**

| Finding ID | Artifact | Detail | MITRE Technique | Assertion SQL |
|-----------|---------|--------|----------------|--------------|
| f47874f1 | Registry Run Key (`registry_runkeys`) | A Run registry key loads `GoogleUpdate.exe` from the user's AppData directory, indicating persistence via a user-level Run key. Evidence confirmed from the `registry_runkeys` table with 1 matching row proved by the assertion engine. | T1547.001 | `SELECT * FROM registry_runkeys WHERE value_data LIKE '%GoogleUpdate.exe%'` |

**Investigation notes:** **Investigation notes:** The agent analyzed the `registry_runkeys` artifact category extracted from the NFURY Windows 7 image and executed the assertion query `SELECT * FROM registry_runkeys WHERE value_data LIKE '%GoogleUpdate.exe%'`. The query returned one confirmed match, proving that a Run registry key was configured to launch `GoogleUpdate.exe` from the user’s AppData directory. The agent classified this as suspicious persistence because the executable name mimics a legitimate Google Update component while executing from a user-writable location rather than the standard Google installation directory. The finding was mapped to MITRE ATT&CK technique `T1547.001` (Registry Run Keys / Startup Folder). No inferred findings or unverified claims were accepted, as the assertion engine required direct SQL-backed proof before confirmation. The investigation maintained evidence integrity through enforced read-only query execution, SHA256 audit chaining, and replayable forensic validation via `python3 replay.py --finding_id f47874f1`.

## Case 3 — TDungan Windows XP (E01)

**Source:** Ali Hadi DFIR competition image. Windows XP disk with simulated intrusion artifacts. Available at https://github.com/ashemery/LinuxForensics

**What the agent found:**

| Finding ID | Artifact | Detail | MITRE Technique | Assertion SQL |
|-----------|---------|--------|----------------|--------------|
| 791125af | MFT Events (`mft_events`) | Presence of `a.exe` in user Temp directories (e.g., `/Local Settings/Temp/a.exe`) suggests a potentially malicious executable masquerading with a generic single-character filename | T1036.005 | `SELECT * FROM mft_events WHERE filename = 'a.exe' AND full_path LIKE '%Temp%'` |
| 9a878da3 | Prefetch Events (`prefetch_events`) | Execution of generic `A.EXE` observed via Prefetch artifacts, confirming that the suspicious executable was launched on the system | T1204.002 | `SELECT * FROM prefetch_events WHERE executable_name LIKE 'A.EXE%'` |

**Investigation notes:** The agent analyzed both filesystem timeline artifacts (`mft_events`) and execution artifacts (`prefetch_events`) from the TDUNGAN Windows XP image. A suspicious executable named `a.exe` was identified within user Temp directories through the assertion query `SELECT * FROM mft_events WHERE filename = 'a.exe' AND full_path LIKE '%Temp%'`, which returned four confirmed rows. The agent classified this as potential masquerading activity because the binary used a highly generic single-character filename and was stored in a temporary user-writable location commonly abused by attackers.

To validate execution, the agent independently queried Prefetch artifacts using `SELECT * FROM prefetch_events WHERE executable_name LIKE 'A.EXE%'`. The query returned four confirmed execution traces, proving that the suspicious binary had been launched on the system. The findings were mapped to MITRE ATT&CK techniques `T1036.005` (Masquerading) and `T1204.002` (User Execution: Malicious File). By separating file presence from execution evidence, the investigation established both artifact-level placement and runtime confirmation without relying on inferred claims. All findings were validated through the SQL assertion gate, replayable audit chains, and enforced read-only forensic querying.

## Case 6 — Ali Hadi Challenge #1: XAMPP Web Server (E01)

**Source:** Ali Hadi DFIR Challenge #1 — . Available at https://www.ashemery.com/dfir.html

**What the agent found:**

| Finding ID | Artifact | Detail | MITRE Technique | Assertion SQL |
|-----------|---------|--------|----------------|--------------|
| 49df1cba | MFT Timeline (`mft_events`) | Numerous files identified under `/mnt/windows_c/xampp/htdocs`, confirming the presence of a XAMPP web server installation exposed through the web root directory | T1082 | `SELECT * FROM mft_events WHERE full_path LIKE '%/xampp%'` |
| ef019ecf | MFT Timeline — XAMPP htdocs (`mft_events`) | `phpinfo.php` identified inside the XAMPP `htdocs` directory, potentially usable for web shell activity or server information disclosure | T1505.003 | `SELECT * FROM mft_events WHERE filename = 'phpinfo.php' AND full_path LIKE '%/xampp%/htdocs%'` |

**Investigation notes — adaptive strategy:** The agent initially performed standard compromise triage by searching for suspicious executables in `%AppData%` and `%Temp%`, but these queries did not immediately align with the observed environment. After parsing the MFT timeline, the agent identified the presence of a XAMPP web server installation and adapted its strategy accordingly.

The investigation pivoted from traditional endpoint-focused indicators to web server artifact analysis, specifically targeting `.php` files within the `htdocs/` directory. This shift led to the identification of `phpinfo.php` in the web root. The presence of this file in `htdocs` is significant because it can expose detailed server configuration information when accessed via HTTP, making it a common reconnaissance or initial compromise indicator in web server attacks.

The adaptive transition from endpoint persistence hunting to web-focused artifact discovery was driven by environmental context rather than predefined rules, highlighting a context-aware forensic approach.

## Case 7 — Rocba C-Drive (E01)

**Source:** [SANS Find Evil! Hackathon 2026 Provided Evidence](https://sansorg.egnyte.com/fl/HhH7crTYT4JK#folder-link/HACKATHON-2026)

**What the agent found:** Zero confirmed findings.

**Investigation evidence queried:**

| Artifact Category | Query Summary | Result |
|------------------|--------------|--------|
| MFT timeline (`mft_events`) | Full filesystem timeline review including user directories, temp paths, and staged data locations linked to exfiltration activity | No additional hits beyond known exfiltration paths |
| Registry run keys (`registry_runkeys`) | HKCU and HKLM persistence review for startup or stealth execution mechanisms related to insider activity | No persistence entries detected |
| Prefetch records (`prefetch_events`) | Execution history analysis for known tools such as SDelete, Sysinternals utilities, and cloud sync agents | No direct attacker tool execution traces confirmed in Prefetch |
| Event logs (`evtx_events`) | Authentication, privilege escalation, and lateral movement behavior analysis across system logs | No suspicious login or escalation patterns identified |
| Dropped tools / binaries | Search for known offensive tooling including Mimikatz, PsExec, Netcat, and C2 implants | No known attacker tools or implants discovered |

**Cross-case synthesis — Rocba intrusion (disk vs memory correlation):**

Cases 5 and 7 together describe two different visibility layers of the same intrusion:

* **Case 5 (ROCBA Memory Analysis):** `svchost.exe` PID 1248 exhibited abnormal behavior with 190 active external network connections to `81.30.144.115`, consistent with command-and-control communication and potential exfiltration activity (T1041).
* **Case 7 (ROCBA Disk Image):** No supporting disk artifacts were identified — no dropped binaries, no known tooling (Mimikatz, PsExec, Netcat), and no persistence mechanisms such as registry run keys or scheduled execution traces.

**Combined interpretation:** The discrepancy between volatile memory activity and the absence of disk-based artifacts strongly indicates a fileless execution pattern. The malicious activity is resident in memory only, with no corresponding on-disk footprint such as staged payloads or installed tools.

This alignment supports a **fileless malware / memory-resident execution model**, where the attacker operates through in-memory processes (e.g., injected or hijacked system processes like `svchost.exe`) while deliberately avoiding disk writes to evade forensic acquisition and traditional endpoint detection.

The conclusion is derived strictly from cross-artifact correlation between memory telemetry and disk absence, rather than any single data source in isolation.

###  Observed System Behavior & Analytical Stress Points

This case exposed important operational and architectural constraints in multi-agent forensic reasoning systems:

**1. Evidence Dilution Under High Volume**
- As dataset size increases, high-signal artifacts (e.g., Recycle Bin payloads, rare executables) become statistically “hidden” among benign entries.
- Without targeted querying, the agent defaults to high-frequency artifacts (e.g., OneDrive.exe, system binaries), missing low-frequency malicious indicators.

**2. Query Narrowing Bias**
- Early-stage filters (e.g., XAMPP, htdocs, web server assumptions) caused premature path specialization.
- This demonstrates a risk of *contextual anchoring bias* where the model overfits an initial hypothesis instead of re-scanning the full evidence space.

**3. Conclusion Compression Failure**
- During final summarization, multiple valid low-level signals were aggregated into generic statements.
- This reduces forensic precision by collapsing distinct artifacts into “general compromise indicators” rather than preserving traceable evidence chains.

**4. Tool Exhaustion vs. Evidence Exhaustion Mismatch**
- Coverage logic reached 100%, but that metric reflects tool usage completeness, not investigative depth.
- This creates a false sense of completion even when high-value artifacts remain underexplored.

---

###  Engineering Insights Derived from This Case

This case directly informed several critical design principles for SIFT-PROOF:

- Evidence must be **retrieval-driven before reasoning-driven**
- Coverage metrics must evolve from “tool completion” → **artifact confidence scoring**
- Large datasets require **adaptive query expansion**, not fixed iteration limits
- Findings must remain **atomized and traceable**, not merged prematurely in summarization

---

###  Roadmap Evolution: SIFT-PROOF Next Stage Improvements

Based on the Vanko case behavior, the next evolution of SIFT-PROOF is defined as follows:

#### 1. Evidence-First Reasoning Engine
All conclusions must be backed by:
- explicit SQL queries
- reproducible result sets
- artifact-level provenance mapping

#### 2. Adaptive Deep Search Layer
Introduce a second-pass reasoning mode that activates when:
- dataset size exceeds threshold (e.g., >100k rows)
- or signal density drops below expected anomaly rate

This ensures low-frequency artifacts are not lost in bulk analysis.

#### 3. Multi-Artifact Correlation Graph
Replace linear reasoning with a graph model:
- MFT ↔ Prefetch ↔ Amcache ↔ Registry ↔ EVTX
- Cross-link execution → persistence → user activity chains

This enables true “kill chain reconstruction” rather than isolated findings.

#### 4. False Completion Guardrail
Prevent premature termination when:
- only structural coverage is complete
- but anomaly density is still statistically low

Introduce a second metric:
> “Investigative confidence score” (not just tool coverage)

#### 5. Forensic Explainability Layer
Every finding must include:
- raw query used
- source table
- evidence row preview
- reasoning link to MITRE mapping

###  Summary Insight

The Vanko case demonstrated that **scaling forensic AI is not about adding more tools — it is about controlling reasoning depth under data pressure.**

This case is now the blueprint for transforming SIFT-PROOF from:
> a tool execution engine  
to  
> a **verifiable, evidence-driven forensic reasoning system**


## Competition Context

This submission was prepared for the **SANS SIFT Find Evil! Hackathon 2026**. The investigation framework is designed to simulate real-world DFIR workflows using isolated forensic environments per case.

All real-world images used (Cases 2–7) are publicly available DFIR competition artifacts from established training and challenge series used widely in academic and professional digital forensics contexts. No real victim data, personal information, or confidential operational datasets are included.

Primary sources include:
- SANS Find Evil! Hackathon 2026 provided evidence repository
- Ali Hadi DFIR challenge series (publicly distributed forensic training images)

Each case is intentionally structured as an independent forensic scenario to ensure reproducibility, auditability, and fairness in evaluation.
